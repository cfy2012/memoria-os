# 版本规则

## 一句话

第三位是奇数 → beta（测试版），偶数 → stable（稳定版）。

自 1.6.1 之后生效：

| 版本 | 类型 | 内容 |
|---|---|---|
| 1.6.1 | 历史遗留 | 未按规则分类，当时还没有这套约定 |
| 1.6.2 | stable | 双挂载点前置修复 |
| 1.6.3 | beta | 启动卡改屏幕 TF 卡槽，SD 大卡降为 `/sd_ext` 扩展盘 |
| 1.6.4 | stable | 分区表改 `ota_0` + `ota_1` 双槽，删 `factory`，补 OTA 自校验 |
| 1.6.5 | beta | 用户数据整体搬 TF 卡（`memoria_vault` + PrivateFs 换后端），flash 只留系统 |
| 1.6.7 | beta | OTA 修通（crt bundle）+ 身份校验（项目名/版本）+ 盖章后移到进桌面 30 秒 |
| 1.6.9 | beta | OTA 下载全程 sha256 校验（弃用 esp_https_ota 改流式）+ 版本比较抽成 host 可测 + CI 单测 job |
| 1.6.6 | stable | 顺延：1.6.5 未上板即被 1.6.7 取代，转正号留给 1.6.7 验证通过后 |

## 为什么要分

beta 位用来装**激进改动**：分区表、驱动替换、屏幕接口切换、自检固件。这些东西一旦在别人板子上出问题，代价是"开不了机"。stable 位只装 beta 上板验证过的东西。

有了这个划分，OTA 才能分层：stable 只推 stable 包，别人不会因为一次实验性改动把机器刷成砖。

## 发布流程

1. 新功能进下一个**奇数**版本。
2. 上板跑一遍，把串口日志留档；跑几天日常使用。
3. 没问题 → 下一个**偶数**版本转正，`CHANGELOG` 里写明"由 1.6.x 转正"。
4. 出问题 → 这个 beta **不转正**，修完直接跳到下一个奇数（1.6.5 坏了就出 1.6.7），不占用偶数号。偶数号一旦占用就是"已验证"的承诺。

## 机器怎么知道自己是哪个

`firmware/version.json` 增加 `channel` 字段：

```json
{
  "version": "1.6.4",
  "channel": "stable",
  "major": "false"
}
```

`test/checks/versions.py` 每次都校验它和版本号奇偶是否一致，写错了 CI 直接红。OTA 客户端目前只读取展示，不做拦截——等双通道分发真正跑起来再收紧。

## 一个必须记着的事实

1.6.4 按规则归为 stable，但它是**分区表 A/B 改造**，一次真机都没跑过。也就是说 1.6.4 这个 "stable" 是名义上的，实际风险等同于 beta。

真正严格按规则执行，从 **1.6.5** 开始。1.6.5 上板验证通过、1.6.6 转正之后，stable 这个词才算有内容。
